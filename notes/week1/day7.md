# Day 7：第一周复盘

## 一、闭环用例和分散用例的区别

| 类型 | 测什么 | 例子 |
|---|---|---|
| 分散用例 | 单个接口的行为 | 只测创建、只测查询 |
| 闭环用例 | 接口之间的协作 | 创建 → 查询 → 更新 → 删除 → 确认 404 |

闭环用例的价值：发现“单个接口都正常，组合起来却出问题”的情况。

## 二、闭环用例覆盖的链路
- POST /booking → 200，拿到 bookingid
- GET /booking/{id} → 200，字段正确
- PUT /booking/{id} → 200，字段已更新
- DELETE /booking/{id} → 200 或 201
- GET /booking/{id} → 404，确认已删除


## 三、这次遇到的一个真实错误

**现象**：创建接口连续 3 次返回 500。

**原因**：测试代码漏传了 `json=payload`，服务端收到空请求体。

**教训**：

- 500 不一定是服务端故障，也可能是客户端参数错误
- 重试策略要结合请求内容判断，不能盲目重试
- 500 加空请求体，重试 3 次也只是浪费请求

## 四、面试问题补充

### Q1：闭环用例和单接口用例，哪个更重要？

- 两者都重要，职责不同
- 单接口用例定位问题快，失败时知道是哪个接口
- 闭环用例验证业务流程，发现接口协作问题
- 生产级测试两者都要有

### Q2：为什么创建 booking 不需要 token，更新和删除需要？

- 这是 Restful-Booker 的设计
- 创建是匿名操作，任何人都能创建
- 更新和删除会改变已有数据，需要鉴权
- 真实项目里，鉴权规则取决于业务：什么操作需要登录、什么操作需要角色权限

### Q3：如果创建接口偶发 500，你怎么区分是代码问题还是服务问题？

- 看日志：请求体、响应体、状态码
- 看重现率：每次都 500 还是偶发
- 看请求内容：参数是否完整、格式是否正确
- 看其他接口：其他接口正常，可能只是这个接口的问题
- 用 Postman/curl 手动复现，排除测试代码问题

### Q4：写闭环用例时，前一步失败怎么办？

- 用 assert 让测试立即失败，后续步骤不执行
- 不要吞掉失败继续跑，否则会得到连锁的错误结果
- 可以在 assert 的失败信息里带上上下文，便于定位
- 如果业务上允许多种结果，用 `in (200, 201)` 这类断言
